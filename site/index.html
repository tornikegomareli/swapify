How it works

Two images, pointers in both directions.

swapify compiles the edited file unchanged, with the build's own command, into a dylib. An agent inside the app loads it and rewires the app and the patch so that old callers run new bodies, and new code keeps the old types, objects and storage.

Every function is a door

The app is built with -enable-implicit-dynamic. Each Swift function first asks its chain root $s…TX where its body is. Copying the patch's root into the app's root redirects direct calls, vtable dispatch and protocol witnesses.

New code, old types

The patch carries a second copy of every type in the file. Its metadata accessors and addressors jump to the app's, and its field offsets and witness tables are copied over, so @State, singletons and casts survive.

A layout guard

Before patching, the agent compares each nominal type descriptor $s…Mn with the app's: field names, types and vtable size. A changed layout is refused, and the agent is told to rebuild.

SwiftUI redraws, state kept

The agent invalidates each _UIHostingView graph the way Xcode Previews does, but without the phase change that resets @State. Then it renders a 1x snapshot and reads the accessibility tree.

Scope

What reloads.

Anything that keeps the memory layout of existing objects reloads. The guard catches the rest.

Bodies of functions, methods, initializers, computed propertieslive
SwiftUI structure and modifiers, with @Statelive
